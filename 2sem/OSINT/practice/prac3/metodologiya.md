## 1. Общий подход к выполнению работы

### Что требуется сделать

Реконструировать **полный публичный цифровой контур** организации (не только основной сайт) по **разнородным открытым данным**. Нужно:
- Найти основной домен и обосновать его статус
- Выявить связанные домены, поддомены и сервисные контуры
- Построить реестр артефактов с классификацией по типу источника
- Разделить все связи на подтверждённые, вероятные и спорные
- Восстановить историческую эволюцию контура
- Выделить публикационные, кадровые и документационные следы

### Важное отличие от предыдущих работ

Практика 3 фокусируется не на «технических следах и рисках» (как практика 2) и не только на DNS/сетевой инфраструктуре (как практика 1), а на **комплексной реконструкции всего цифрового контура** — доменного, сервисного, документационного, кадрового и публикационного.

**Ключевые различия:**

| Практика 1 | Практика 2 | Практика 3 |
|---|---|---|
| DNS + сеть + ASN | Тех-следы + риски публикаций | Полный контур + корреляция |
| Глубокий DNS | Анализ вакансий и блогов | Классификация по уверенности |
| Карта по DNS | Рисковая матрица | Исторический блок |
| | | Карта артефактов |

### Рекомендуемый объект

**Яндекс** (вариант 5 — новостной/отраслевой медиаресурс):
- Медийная платформа Дзен (dzen.ru) ранее была частью Яндекса
- Технологический блог tech.yandex.ru — крупный отраслевой ресурс
- Публичная документация, OSS-проекты, конференции
- Богатая история изменений контура (27+ лет)

### Шаг 1. Выберите вариант и объект

**Яндекс подходит:** Дзен (медиа), tech.yandex.ru (технологический блог), YDB/YTsaurus (OSS), публичные конференции.

### Шаг 2. Сформулируйте цель исследования

Цель — не просто описать инфраструктуру (это делалось в практике 1), а **реконструировать полный контур** по всем разнородным источникам и классифицировать связи по уровням уверенности.

**Как формулировать цель (пример):**

> Реконструкция публичного цифрового контура Яндекса по разнородным открытым данным: доменным, сервисным, документационным, кадровым и публикационным следам с разделением по уровням уверенности.

### Шаг 3. Сформулируйте гипотезы

В отличие от практик 1 и 2, здесь нужны гипотезы о **структуре контура**, а не о его рисках:

> **Гипотеза 1:** Цифровой контур Яндекса не исчерпывается основным доменом yandex.ru/ya.ru и включает разветвлённую сеть поддоменов по функционалу (облако, маркетплейс, OAuth, CDN).
>
> **Гипотеза 2:** Help-/docs-контур (Yandex Cloud Docs, YDB docs, YTsaurus docs) подтверждает вынесение части функционала на публичные API-платформы.

> **Гипотеза 3:** Вакансионные страницы раскрывают реальную организационную структуру и технологический стек, не отражённый на основном сайте.
>
> **Гипотеза 4:** Open-source релизы (YDB, YTsaurus) являются самостоятельными точками входа в цифровой контур, с собственными доменами и поддоменами.

### Шаг 4. Определите классы источников

## 3. Этап 2. Определение основного домена

### Шаг 1. Выявите все кандидаты на основной домен

Для Яндекса кандидатов несколько:
- **yandex.ru** (1997 г.) — исторический основной
- **ya.ru** (2008 г., стал главной в 2022) — текущая точка входа
- **yandex.com** — международный домен
- **yandex.net** — инфраструктурный

### Шаг 2. Для каждого кандидата соберите данные

Для каждого кандидата проверьте:

```bash
# WHOIS
whois yandex.ru
whois ya.ru
whois yandex.com
whois yandex.net

# DNS-записи
dig yandex.ru +short
dig ya.ru +short
dig yandex.com +short
dig yandex.net +short

# HTTP-заголовки
curl -I https://yandex.ru
curl -I https://ya.ru
curl -I https://yandex.com
curl -I https://yandex.net
```

### Шаг 3. Обоснуйте выбор основного домена

Используйте три критерия:
1. **Исторический** — самый старый, первый зарегистрированный
2. **Функциональный** — основной DNS, MX, HTTPS
3. **Пользовательский** — куда направляется основной трафик

**Пример обоснования:**

> Домен `yandex.ru` является основным с точки зрения истории регистрации (1997 г.) и DNS-инфраструктуры. Однако с сентября 2022 г. основной публичный вход перенесён на `ya.ru` (302 редирект), при этом `yandex.ru` сохранил все сервисные функции.

### Шаг 4. Проверьте взаимосвязь доменов

```bash
# Редиректы
curl -L -I https://yandex.ru | grep -i location

# Единая cookie-область
curl -I https://ya.ru | grep -i set-cookie

# Совпадение IP-адресов
dig yandex.ru +short
dig ya.ru +short
```

**Ключевой вывод:** если домены резолвятся в один ASN, имеют одинаковые cookie-домены, или redirect 302 — это один контур.

### Что должно получиться к концу этапа

Паспорт каждого кандидата (WHOIS, DNS, ASN, HTTP) + обоснование, почему выбранный домен считается основным.

## 4. Этап 3. Поиск связанных доменов и поддоменов

### Шаг 1. Ищите через публичную документацию

Документация — самый надёжный источник:

```
Идите по ссылкам:
1. cloud.yandex.ru/docs — все облачные сервисы
2. yandex.com/dev — OAuth и API
3. tech.yandex.ru — технологический блог
4. developer.yandex.ru — developer portal
5. github.com/yandex — open-source проекты
```

**Как искать (пример):**
- `cloud.yandex.ru` → `msp.yandex.net`, `k8s.yandex.net`
- `oauth.yandex.com` → `id.yandex.net`, `passport.yandex.ru`
- `ydb.tech` → `yandex.github.io/ydb`

### Шаг 2. Ищите через SSL-сертификаты (crt.sh)

```
Зайдите на crt.sh и выполните поиск по:
1. yandex.ru — все поддомены с сертификатом
2. *.yandex.ru — wildcard-сертификаты
3. yandex.net — инфраструктурные домены
4. yandex-cloud — облачные сервисы
```

**Что это даёт:** Поддомены, которые не указаны в документации, но имеют публичные сертификаты.

**Пример найденных поддоменов через crt.sh:**
- `imap.yandex.ru`, `smtp.yandex.ru` — почтовый контур
- `mc.yandex.net` — мониторинг
- `dr.yandex.net`, `dr2.yandex.net` — NEL-эндпоинты
- `ydb.tech`, `ytsaurus.tech` — OSS-продукты

### Шаг 3. Ищите через ASN-реестры

```
1. bgp.he.net/AS13238 — основной ASN Яндекса
2. bgp.he.net/AS200350 — Yandex Cloud
3. ipinfo.io/AS13238 — IP-диапазоны
```

**Как использовать:** Посмотрите на все домены, резолвящиеся в IP-адреса Яндекса — это могут быть дополнительные сервисы.

### Шаг 4. Ищите через CSP-заголовки

```bash
# Получите CSP-заголовок
curl -s https://ya.ru | grep -i content-security-policy
```

CSP-заголовок содержит **все доверенные домены** — это готовый инвентарь сервисных контуров:
- `yastatic.net` — CDN
- `mc.yandex.ru` — метрика
- `ads.adfox.ru` — реклама

### Шаг 5. Ищите через domain verification TXT-записи

```
Проверьте TXT-записи домена:
dig yandex.ru TXT +short

Ищите:
- "google-site-verification=..." — связь с Google
- "facebook-domain-verification=..." — связь с Facebook
- "ms=..." — связь с Microsoft
- "mail.ru/..." — связь с Mail.ru
```

**Что это даёт:** Список внешних интеграций, который организация не публикует на сайте.

### Шаг 6. Ищите через вакансионные и публикационные страницы

```
1. tech.yandex.ru/career — список технологий и команд
2. hh.ru/yandex — детальные описания стека
3. infraevents.yandex.ru — конференции
4. habr.com/ru/company/yandex — техническое сообщество
```

### Шаг 7. Группируйте найденные домены по функциям

```
Облачные вычисления:    cloud.yandex.net, cloud.yandex.ru
Авторизация:             oauth.yandex.com, oauth.yandex.ru
Маркетплейс:            market.yandex.ru
CDN / статика:          yastatic.net, *.yastatic.net
Медиа:                  dzen.ru, dzen.yandex.net
Почта:                  mail.yandex.ru, imap.yandex.ru
Мониторинг:             mc.yandex.net
Open-source:            ydb.tech, ytsaurus.tech, diplodoc.tech
Конференции:            infraevents.yandex.ru
```

### Что должно получиться к концу этапа

Список из 15–20+ связанных доменов, сгруппированных по функциональным категориям.


## 7. Этап 6. Классификация по уровням уверенности

### Шаг 1. Разделите наблюдения на три группы

**Группа 1: Подтверждённые (confirmed)**
Прямое доказательство из публичного источника:
- DNS-запись A → IP в ASN Яндекса
- WHOIS → владелец Yandex LLC
- OAuth-эндпоинт → публичная спецификация
- TXT-запись domain verification → подтверждённая интеграция
- Публичная документация → подтверждённый сервис

**Группа 2: Вероятные (probable)**
Выведено по косвенным признакам:
- DNS-паттерн `*.yandex.ru` → предполагаемый поддомен
- WHOIS-паттерн → возможный домен без DNS-resolve
- Вакансии → предполагаемый стек без подтверждения по артефактам

**Группа 3: Спорные / неполные**
Невозможно подтвердить пассивными методами:
- Внутренние сервисы (CI/CD, мониторинг, БД)
- Часть поддоменов не публична
- Вакансионные данные могут быть устаревшими

### Шаг 2. Для каждого наблюдения укажите основание

```
| № | Наблюдение | Основание | Уровень уверенности | Примечание |
|---|---|---|---|---|
| 1 | Единая DNS-инфраструктура | DNS + dnsviz.net | Подтверждено | Собственная DNS + DNSSEC |
| 2 | OAuth-контур oauth.yandex.com | OAuth2-spec | Подтверждено | PKCE (S256) |
| 3 | travel.yandex.ru — активный | DNS-паттерн | Вероятно | HTTP-доступен |
```

### Шаг 3. Выделите «спорные» наблюдения отдельно

```
| Наблюдение | Почему спорно |
|---|---|
| career.yandex.ru HTTP 404 | URL может быть изменён |
| Полное количество поддоменов | DNS-паттерны ≠ полнота |
| mc.yandex.net → Метрика | Корреляция по паттерну |
```

### Что должно получиться к концу этапа

Три таблицы: подтверждённые, вероятные и спорные наблюдения с основаниями.

## 9. Этап 8. Формулировка ограничений и выводов

### Шаг 1. Выделите ограничения

В отличие от практик 1 и 2, здесь ограничения важно связать с **уровнем уверенности**:

```
1. Пассивные данные. DNS, WHOIS, TLS-сертификаты, публичная документация использованы без активного сканирования.
2. DNS-паттерны ≠ доказательства. Поддомены по шаблонам (travel, maps, taxi) не подтверждены напрямую.
3. Вакансионные данные могут быть устаревшими. Не все технологии из вакансий актуальны.
4. Часть контура не публична. Внутренние сервисы, CI/CD частично скрыты.
5. CSP-заголовки могут быть неполными. Не все сервисные домены включены в CSP.
6. Исторические traces неполные. web.archive.org архивирует не все страницы.
```

### Шаг 2. Сформулируйте аналитический вывод

Вывод должен ответить на вопрос: **полный ли цифровой контур выявлен?**

**Структура вывода:**
1. Основной тезис (контур обнаружен частично или полностью?)
2. Перечень подтверждённых контуров (OAuth, Cloud, OSS, Media и т.д.)
3. Перечень вероятных контуров (Maps, Taxi, Travel — по DNS-паттерну)
4. Организационные выводы (распределённая структура, внешние зависимости)
5. Итоговый тезис (контур — это не домен, а сеть контуров)

**Пример:**
> Цифровой контур Яндекса — это не единый домен, а сеть взаимосвязанных доменов и сервисов, объединённых единой ASN-инфраструктурой (AS13238/AS200350).

### Что должно получиться к концу этапа

Раздел с 5–6 ограничениями + развёрнутый аналитический вывод.

## Как отвечать на контрольные вопросы

### Вопрос 1: Что понимается под публичным цифровым контуром организации?

**Ответ:** Публичный цифровой контур — совокупность всех публично наблюдаемых доменных, сервисных, публикационных, кадровых, документационных и исторических следов, через которые организация представлена в цифровой среде. Это не только основной сайт, но и OAuth-платформы, облачные API, CDN, медиа-платформы, open-source проекты, почтовые и мониторинговые сервисы, технологические блоги, карьерные страницы.

### Вопрос 2: Почему основной домен нельзя считать достаточным описанием?

**Ответ:** Основной домен (yandex.ru) — лишь одна из десятков точек входа. По отдельности он не раскрывает: OAuth-контур, облачную платформу, OSS-продукты, медийный бизнес, инфраструктурные ASN, CDN и внешние интеграции. Реконструкция требует анализа разнородных источников.

### Вопрос 3: Какие классы источников особенно важны?

**Ответ:** Доменные и DNS-данные, TLS-сертификаты, ASN-реестры, публичная документация, вакансии, OSS-репозитории, CSP-заголовки, domain verification TXT-записи, архивные копии. Каждый класс раскрывает свой фрагмент: DNS — домены, вакансии — стек, CSP — доверенные сервисы, domain verification — партнёрства.

### Вопрос 4: Чем подтверждённая связь отличается от вероятной?

**Ответ:** Подтверждённая связь — элемент найден через прямой источник (DNS A-запись, WHOIS, публичная документация, OAuth-endpoint). Вероятная связь — выведена по паттерну (DNS-шаблон `*.yandex.ru`) без прямого подтверждения.

### Вопрос 5: Какую роль играют help-ресурсы и документация в OSINT-анализе?

**Ответ:** Документация раскрывает API-контур, интеграционные паттерны, SDK (Go/Python/Java/Node.js), Terraform Provider, архитектурные принципы. Каждый OSS-проект с собственным доменом (ydb.tech, ytsaurus.tech) — самостоятельная точка входа в цифровой контур.

### Вопрос 6: Почему кадровые публикации полезны?

**Ответ:** Вакансии показывают реальную организационную структуру: 600+ разработчиков, 150+ ML-инженеров, 150+ аналитиков, 200+ C++-инженеров. Раскрывают технологический стек (Go, C++, Python, Java, PyTorch, TensorFlow) — фрагмент пазла, который невозможно получить из DNS-данных.

### Вопрос 7: Зачем выделять ограничения исследования?

**Ответ:** Публичные данные всегда неполны: DNS-паттерны ≠ подтверждения, вакансии ≠ текущий стек, CSP ≠ полный инвентарь. Без ограничений выводы могут быть ошибочно интерпретированы как полные.

### Вопрос 8: Почему карта цифрового контура важнее простого списка артефактов?

**Ответ:** Карта показывает **структуру связей**: домен → сервис → инфраструктура → внешние интеграции. Список артефактов не показывает, что OAuth связывает все продукты, что CDN связывает все домены, что ASN-инфраструктура объединяет все контуры. Карта — аналитическая модель, список — инвентарь.
