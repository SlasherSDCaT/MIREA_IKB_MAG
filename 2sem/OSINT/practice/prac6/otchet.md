**Профиль:** «Киберразведка и противодействие угрозам с применением технологий искусственного интеллекта»

## 1. Аналитическая задача и паспорт исследования

### Аналитическая задача

**Вопрос картирования:** Какие субъекты, ресурсы, события и индикаторы образуют публичную цифровую экосистему технологической платформы Yandex как SaaS-сервиса, и какие отношения между ними подтверждаются открытыми источниками?

**Период исследования:** 2020–2026 гг.
**Границы:** Публичные источники, пассивные методы OSINT. Активное сканирование не проводилось.

### Форма 1. Паспорт исследования

| Поле | Содержание |
|------|-----------|
| **Вариант** | Вариант 10. SaaS-сервис (общего назначения) |
| **Объект исследования** | Яндекс (Yandex) — SaaS-технологическая платформа / технологическая экосистема |
| **Отрасль** | IT, облачные вычисления, SaaS-платформы, поисковые технологии |
| **Аналитическая задача** | Построение карты связей между субъектами, ресурсами, событиями и индикаторами экосистемы Яндекса на основе открытых данных |
| **Исходные гипотезы** | **Гипотеза 1:** Экосистема Яндекса формируется вокруг нескольких устойчивых групп сущностей (основной субъект, облачные ресурсы, образовательные события, OSS-проекты), связанных повторяющимися индикаторами.<br><br>**Гипотеза 2:** Часть связей между субъектами подтверждена прямыми указаниями (прямое партнёрство, совместные публикации), часть — косвенными индикаторами (совпадающие домены, одинаковые команды).<br><br>**Гипотеза 3:** Событийные публикации (конференции, релизы, вакансии) являются наиболее информативным источником связей между субъектами и ресурсами.<br><br>**Гипотеза 4:** Исторические сущности (dzen.yandex.net, career.yandex.ru) создают шум и требуют разграничения с текущими связями. |

## 3. Нормализация сущностей

### 3.1. Выполненные операции нормализации

| Операция | Описание | Пример |
|---------|---------|------|
| **Унификация регистра** | Все доменные имена приведены к нижнему регистру | `Yandex.ru` → `yandex.ru` |
| **Нормализация ID** | Каждой сущности присвоен уникальный идентификатор с префиксом типа | `Яндекс` → `SUBJ-01`, `ya.ru` → `RES-01` |
| **Удаление дублей** | Убраны дублирующие сущности с одинаковым содержанием | `cloud.yandex.net`, `Cloud.Yandex.Net` → `cloud.yandex.net` |
| **Разделение текущего и исторического** | Сущности помечены статусом текущего/исторического значения | `dzen.yandex.net` → `EVT-02` (исторический), `dzen.ru` не включён |
| **Группировка по типу** | Сущности сгруппированы по 4 типам с префиксами ID | SUBJ-*, RES-*, EVT-*, IND-* |

### 3.2. Обнаруженные дубли и их обработка

| Дубль | Исходные формы | Действие |
|------|-------------|---------|
| Облачный контур | `Cloud.Yandex.Net`, `cloud.yandex.net`, `Cloud yandex.net` | Унификация к `cloud.yandex.net` (RES-04) |
| OAuth-контур | `oauth.Yandex.com`, `oauth.yandex.com` | Унификация к `oauth.yandex.com` (RES-03) |
| DNS NS | `ns1.Yandex.ru`, `ns1.yandex.ru` | Унификация к `ns1.yandex.ru` (IND-01) |

| Карьерная страница | `career.yandex.ru` (HTTP 404) | Исключена из реестра как неактивная |

### 6.2. Легенда карты

| Элемент | Обозначение | Описание |
|--------|-----------|---------|
| `Субъект (SUBJ-*)` | ╔══╗ | Организация, подразделение, проект, команда |
| `Ресурс (RES-*)` | ╔══╗ | Сайт, поддомен, документ, репозиторий |
| `Событие (EVT-*)` | ╔══╗ | Публикация, релиз, конференция, выделение |
| `Индикатор (IND-*)` | ═══ | Домен, URL, дата, заголовок, TXT-запись, ASN |
| `владеет` | ──владеет────> | Субъект владеет/создаёт ресурс (WHOIS, DNS, официальный сайт) |
| `публикует` | ──публикует─> | Субъект публикует контент на ресурсе |
| `содержит индикатор` | ──владеет──> | Ресурс содержит наблюдаемый признак |
| `связало с` | ──связало──> | Событие связывает субъект и ресурс |
| `[Подтверждено]` | | Прямое указание в источнике (официальный сайт, DNS, HTTP) |
| `[Вероятно]` | | Косвенное подтверждение (совпадающие домены, паттерны) |
| `[Верификация]` | | Подтверждено одним источником (TXT-запись) |

## 8. Ограничения исследования

1. **Только пассивные данные.** Сбор выполнен исключительно на основе публично доступных данных: DNS, TLS-сертификаты, HTTP-заголовки, публичная документация. Активное сканирование не проводилось.
2. **DNS-паттерны ≠ доказательства.** Некоторые индикаторы (`imap.yandex.ru`, `smtp.yandex.ru`) выведены по DNS-паттерну без HTTP-подтверждения.
3. **Ограниченность событийных данных.** Информация о событиях (Субботник, выделение Дзена) получена из ограниченного числа публичных источников. Часть внутренних событий могла быть упущена.
4. **Исторические связи неполны.** web.archive.org не архивирует все страницы Яндекса; часть исторических связей может быть не обнаружена.
5. **Косвенные связи требуют осторожности.** Связи с уровнем уверенности «вероятно» (10 из 35) основаны на косвенных признаках и не являются прямыми доказательствами.
6. **Период исследования ограничен.** Данные охватывают период 2020–2026 гг. Более ранние связи (до 2020) могут не отражать полную историю экосистемы.
7. **Персональные данные.** Вакансии и профили сотрудников hh.ru использованы как источники информации о командах, но не содержат персональных данных.

## 11. Контрольные вопросы к защите

### Вопрос 1: Как вы определяли тип связи между сущностями?

**Ответ:** Тип связи определялся на основе характера отношения между сущностями, подтверждённого источником. Если один субъект официально владеет ресурсом (WHOIS, DNS, официальная страница) — тип `владеет`. Если ресурс содержит наблюдаемый признак (DNS-запись, HTTP-заголовок) — `содержит индикатор`. Если событие связывает две сущности во времени — `связало с`. Типы связи — не произвольный выбор, а отражение характера отношения.

### Вопрос 2: Почему вы включили историческую сущность Дзен в карту?

**Ответ:** Дзен (SUBJ-05) включён как историческая сущность, потому что связь `SUBJ-01 → SUBJ-05` (EVT-02 — выделение Дзена в 2022 году) является значимой для понимания эволюции экосистемы. Карта связей должна отражать не только текущее состояние, но и историю изменений. Однако Дзен помечен как исторический, и его связи ограничены одним событием.

### Вопрос 3: Как вы оценивали уровень уверенности для каждой связи?

**Ответ:** Уровень уверенности определялся по трём критериям:
- **Подтверждено:** прямое указание в источнике (WHOIS, DNS A/MX/NS/TXT, HTTP 302/200, OAuth-спецификация, SSL-сертификат).
- **Вероятно:** косвенное подтверждение (совпадающие DNS-паттерны, одинаковые команды, совпадающие домены без прямого указания).
- **Требует проверки:** один источник, недостаточное подтверждение (TXT-запись google-site-verification, индикатор по DNS-паттерну без HTTP).

### Вопрос 4: Что бы вы добавили в карту, если бы сбор данных продолжился?

**Ответ:** При продолжении сбора можно было бы добавить:
- Больше событийных сущностей (релизы CloudAPI, новые OSS-проекты).
- Связи между OSS-проектами (например, YTsaurus ↔ YDB).
- Связи с партнёрами (GlobalSign, Google, Facebook) — как субъектами, а не индикаторами.
- Более точное разделение связей SUBJ-02 (Yandex Cloud) и SUBJ-01 (Яндекс).

### Вопрос 5: Как вы отделяли текущие связи от исторических?

**Ответ:** Историчность определялась по трём маркерам:
1. **HTTP-статус:** 404 (career.yandex.ru) — исключён.
2. **Archive.org:** dzen.yandex.net (исторический) → событие EVT-02.
3. **Официальные источники:** press.yandex.ru — подтверждение выделения Дзена.

Текущие сущности подтверждены HTTP 200/302, DNS A/MX/NS/TXT записями, актуальной документацией.

### Вопрос 6: Почему вы не использовали более сложных типов связей?

**Ответ:** 5 типов связей (владеет, публикует, содержит индикатор, связало с, выделил) охватывают все наблюдаемые отношения. Добавление дополнительных типов (например, «зависит от», «зеркалирует») не увеличивает аналитическую ценность, а снижает читаемость карты. Карта должна быть минимально достаточной.

### Вопрос 7: Какие типичные ошибки при построении карты связей были у вас, и как вы их исправляли?

**Ответ:** Основные ошибки:
1. **Включение дублирующих сущностей** (yandex.ru vs ya.ru) — исправлено через унификацию и нормализацию.
2. **Смешение текущего и исторического** — исправлено через статус текущий/исторический.
3. **Необоснованные связи** — исправлено через требование доказательства для каждой связи.
4. **Слишком широкие типы связей** — исправлено через уточнение типов (владеет, публикует, содержит индикатор).

### Вопрос 8: Какой практический вывод можно сделать по объекту на основе карты связей?

**Ответ:** Публичный цифровой контур Яндекса как SaaS-платформы — это **не единый ресурс, а сеть из нескольких устойчивых групп сущностей**, каждая со своей функцией (доменная, облачная, OSS, событийная). Наиболее надёжно подтверждены связи владения (WHOIS, DNS, OAuth-спецификация), наименее — косвенные событийные связи. Карта помогает увидеть не отдельные следы, а их структуру, что невозможно при чтении отдельных страниц.
