## 1. Общий подход к выполнению работы

### Что требуется сделать

Практика 6 — это **переход от поиска отдельных цифровых следов к построению аналитической карты связей**. Если предыдущие задания были ориентированы на домены, технические артефакты, рискованные публикации, реконструкцию цифрового контура и сравнительный анализ объектов, то данная работа формирует следующий уровень OSINT-аналитики: выявление отношений между сущностями и представление этих отношений в виде проверяемой графовой модели.

**Карта связей** в рамках данной работы понимается как визуальная и табличная модель, отражающая установленные по открытым данным отношения между субъектами, ресурсами, событиями и индикаторами. Такая карта не должна быть декоративной схемой. Она является аналитическим инструментом, который помогает увидеть, какие элементы связаны между собой, какие источники подтверждают связь, где связь является достоверной, а где — только вероятной.

### Чем практика 6 отличается от предыдущих

| Практика 1 | Практика 2 | Практика 3 | Практика 4 | Практика 5 | Практика 6 |
|---|---|---|---|---|---|
| DNS + сеть + ASN | Тех-следы + риски | Полный контур одной | Сравнение 3 объектов | Автоматизация следов | **Карта связей (граф)** |
| Анализ одного объекта | Оценка рисков | Классификация по уверенности | Единая система критериев | Классификатор + скрипт | **Реестр сущностей + реестр связей** |
| Карта одного контура | Публикации + вакансии | Исторический блок | Отраслевые паттерны | Верификация | **Доказательства каждой связи** |
| | | | | | **ASCII-визуализация графа** |

### Рекомендованный объект

**Яндекс** (вариант 10 — SaaS-сервис общего назначения):
- Богатый набор субъектов (компания, подразделения, OSS-сообщество, исторические проекты)
- Множество связанных ресурсов (домены, платформы, документация, OSS)
- Событийная динамика (конференции, релизы, выделения)
- Подтверждённые и вероятные связи для демонстрации градации уверенности

## 2. Этап 1. Постановка задачи и паспорт исследования

### Шаг 1. Сформулируйте аналитическую задачу

Студент выбирает вариант и формулирует задачу **не как «найти всё»**, а как аналитический вопрос. Например:

> «Какие субъекты, ресурсы, события и индикаторы образуют публичную цифровую экосистему технологической платформы Yandex как SaaS-сервиса, и какие отношения между ними подтверждаются открытыми источниками?»

В паспорте фиксируются объект, период, границы исследования и исходные гипотезы.

### Шаг 2. Заполните паспорт исследования

```
| Поле | Содержание |
|------|--|
| Вариант | Вариант 10. SaaS-сервис (общего назначения) |
| Объект | Яндекс (Yandex) — SaaS-платформа |
| Аналитическая задача | Построение карты связей между субъектами, ресурсами, событиями и индикаторами |
| Исходные гипотезы | Г1–Г4 (см. ниже) |
```

### Шаг 3. Сформулируйте гипотезы

Гипотезы должны касаться **структуры связей**, а не отдельных артефактов:

> **Гипотеза 1:** Экосистема объекта формируется вокруг нескольких устойчивых групп сущностей (основной субъект, облачные ресурсы, образовательные события, OSS-проекты), связанных повторяющимися индикаторами.
>
> **Гипотеза 2:** Часть связей между субъектами подтверждена прямыми указаниями (прямое партнёрство, совместные публикации), часть — косвенными индикаторами (совпадающие домены, одинаковые команды).
>
> **Гипотеза 3:** Событийные публикации (конференции, релизы, вакансии) являются наиболее информативным источником связей между субъектами и ресурсами.
>
> **Гипотеза 4:** Исторические сущности создают шум и требуют разграничения с текущими связями.

### Что должно получиться к концу этапа

Готовый паспорт: вариант, объект, аналитическая задача, период, границы, 4 гипотезы.

## 3. Этап 2. Определение типов сущностей

### Шаг 1. Определите типы сущностей

До начала сбора данных задайте, какие классы сущностей будут использоваться. Минимальный набор:

| Тип сущности | Описание | Пример |
|---|---|---|
| **Субъект** | Организация, подразделение, проект, публичная роль, группа | Яндекс, Yandex Cloud, OSS community, Дзен |
| **Ресурс** | Публичный цифровой объект или площадка | ya.ru, cloud.yandex.net, github.com/yandex |
| **Событие** | Наблюдаемое действие или факт во времени | Субботник 2024, выделение Дзена, запуск OAuth |
| **Индикатор** | Наблюдаемый признак, связывающий сущности | DNS NS, MX, ASN, HTTP-заголовок, TXT-запись |

При необходимости допускаются дополнительные типы: документ, публикация, роль, площадка. Важно не создавать слишком много типов, иначе карта станет нечитаемой.

### Шаг 2. Задайте правила для каждого типа

| Правило | Содержание |
|---|---|
| **Субъект** | Должен иметь способность действовать, публиковать, владеть |
| **Ресурс** | Должен быть публичным цифровым объектом с идентификатором (домен, URL, репозиторий) |
| **Событие** | Должно быть привязано ко времени и иметь участников |
| **Индикатор** | Должен быть наблюдаемым и проверяемым признаком |

### Что должно получиться к концу этапа

Фиксированный набор типов сущностей с определениями и примерами.

## 4. Этап 3. Сбор открытых материалов и выделение сущностей

Студент фиксирует источники, из которых будет извлекать сведения:

```
| Источник | Тип источника | Ожидаемая ценность |
|---|---|---|
| Официальные сайты | Официальный | Субъекты, ресурсы, прямые связи |
| Публичная документация | Официальный | Ресурсы, индикаторы |
| DNS-реестры (crt.sh, bgp.he.net) | Публичный реестр | Индикаторы, связи ресурс→индикатор |
| Вакансии и карьерные страницы | Вторичный | Субъекты (команды), события |
| Tech-блоги | Вторичный / Публикационный | Субъекты, события, косвенные связи |
| GitHub (OSS) | Open-source | Субъекты, ресурсы, события |
| Пресс-релизы | Официальный | События, связи между субъектами |
| web.archive.org | Архивный | Исторические сущности, события |
| Архивные версии страниц | Архивный | Исторические ресурсы, события |
| Публичные профили | Вторичный | Субъекты (роли, команды) |
```

### Шаг 2. Соберите сущности по категориям

#### Субъекты

```
Ищем: организации, подразделения, проекты, команды, роли

Источники:
- Официальные сайты → основные субъекты
- tech.yandex.ru → команды (Search Team, инфраструктурные команды)
- github.com/yandex → OSS community
- press.yandex.ru → проекты (Дзен, Cloud)
- вакансии → команды и роли
```

#### Ресурсы

```
Ищем: сайты, поддомены, репозитории, документация, CDN

Источники:
- DNS (dig, whois) → домены, поддомены
- Официальные сайты → сервисы, порталы
- Официальная документация → API, developer portal
- SSL-сертификаты (crt.sh) → поддомены
- Веб-архив → исторические ресурсы
```

#### События

```
Ищем: релизы, конференции, публикации, выделения, инциденты

Источники:
- tech.yandex.ru → публикации, релизы
- infraevents.yandex.ru → конференции
- press.yandex.ru → пресс-релизы
- web.archive.org → исторические события
- github.com/yandex → OSS-релизы
```

#### Индикаторы

```
Ищем: домены, URL, даты, хештеги, заголовки, DNS-записи, ASN

Источники:
- DNS (dig NS, MX, TXT, A) → NS-серверы, MX, SPF, DKIM
- crt.sh → SSL CA
- bgp.he.net → ASN
- curl/DevTools → HTTP-заголовки
- TXT-записи → верификации (Google, Facebook)
```

## 6. Этап 5. Определение типов связей

### Шаг 1. Определите типы связей

Связь — отношение между двумя сущностями, подтверждённое или предполагаемое на основе источника. Рекомендуемые типы:

| Тип связи | Описание | Пример |
|---|---|---|
| **владеет** | Субъект владеет/создаёт ресурс | SUBJ-01 → RES-01 (WHOIS, DNS) |
| **публикует** | Субъект публикует контент на ресурсе | SUBJ-03 → RES-07 (tech blog) |
| **содержит индикатор** | Ресурс содержит наблюдаемый признак | RES-01 → IND-01 (DNS NS) |
| **связало с** | Событие связывает субъект и ресурс | EVT-02 → SUBJ-01 + SUBJ-05 |
| **выделил** | Субъект выделил другой субъект/ресурс | SUBJ-01 → SUBJ-05 (Дзен, EVT-02) |

### Шаг 2. Задайте правила для каждой связи

Каждая связь должна иметь:
- **ID связи** (R-01, R-02, ...)
- **Тип связи** (владеет, публикует, содержит индикатор, связало с, выделил)
- **От субъект/ресурс/событие** → **К субъект/ресурс/индикатор**
- **Уровень уверенности** (подтверждено, вероятно, требует проверки)
- **Доказательство** (прямое указание, косвенное, один источник)
- **Источник** (URL, DNS-команда, HTTP-статус и т.д.)

### Шаг 3. Заполните реестр связей

### Форма 3. Реестр связей / таблица рёбер графа

| ID связи | Тип связи | От | К | Уверенность | Доказательство | Источник |
|---|---|---|---|---|---|---|
| R-01 | владеет | SUBJ-01 | RES-01 | Подтверждено | Официальный редирект ya.ru → yandex.ru | ya.ru HTTP 302 |
| R-02 | владеет | SUBJ-01 | RES-02 | Подтверждено | WHOIS-владелец | WHOIS yandex.ru |
| R-03 | содержит индикатор | RES-01 | IND-01 | Подтверждено | DNS NS-записи | dig NS |
| ... | ... | ... | ... | ... | ... | ... |

### Что должно получиться к концу этапа

Таблица рёбер графа: минимум 20 связей с типами, доказательствами, источниками и уровнями уверенности.

## 7. Этап 6. Оценка доказательности и уровней уверенности

### Шаг 1. Определите уровни уверенности

| Уровень | Определение | Пример доказательства |
|---|---|---|
| **Подтверждено** | Прямое указание в источнике | WHOIS-владелец, DNS A/MX/NS/TXT, HTTP 302/200, OAuth-спецификация, SSL-сертификат |
| **Вероятно** | Косвенное подтверждение | Совпадающие DNS-паттерны, одинаковые команды, совпадающие домены без прямого указания |
| **Требует проверки** | Один источник, недостаточное подтверждение | TXT-запись google-site-verification, индикатор по DNS-паттерну без HTTP |

### Шаг 2. Оцените каждую связь

Для каждой связи из реестра определите:
1. **Доказательство:** что именно подтверждает связь?
2. **Уверенность:** подтверждено / вероятно / требует проверки
3. **Источник:** откуда взято доказательство?

### Шаг 3. Подсчитайте статистику

| Показатель | Формула |
|---|---|
| Подтверждено | Количество связей с доказательством "подтверждено" |
| Вероятно | Количество связей с доказательством "вероятно" |
| Требует проверки | Количество связей с доказательством "требует проверки" |
| Средний уровень уверенности | (подтверждено × 1.0 + вероятно × 0.7 + требует проверки × 0.4) / всего |

## 8. Этап 7. Построение карты связей и анализ структуры

### Шаг 1. Постройте визуализацию карты связей

Карта должна быть:
- **Компактной** — не перегруженной, но доказательной
- **Читаемой** — с легендой, обозначениями типов
- **Проверяемой** — каждая связь объяснима источником

### Рекомендации по ASCII-визуализации

```
┌──────────────────────────────────────────────┐
│           ПУБЛИЧНАЯ ЦИФРОВАЯ ЭКОСИСТЕМА      │
│              (карта связей)                    │
└──────────────────────────────────────────────┘

Субъекты (SUBJ)                    Ресурсы (RES)
╔══════╗          владеет          ╔══════╗
║SUBJ-1├─────────────────────────>║RES-1:  ║
║      ║──владеет──>              ║       ║
║      ║──владеет──>              ║       ║
╚══════╝          публикует        ╚══════╝
         │                           │
         ▼                           ▼
События (EVT)                Индикаторы (IND)
╔══════╗           связало       ╔══════════════════╗
║EVT-1 ├────────────с──>        ║RES-1 содержит:    ║
║      ║                           ║  IND-1: DNS NS   ║
╚══════╝                           ║  IND-2: MX       ║
                                   ╚══════════════════╝
```

### Шаг 2. Добавьте легенду

| Элемент | Обозначение | Описание |
|---|---|---|
| Субъект | ╔══╗ | Организация, подразделение, проект |
| Ресурс | ╔══╗ | Сайт, поддомен, документ, репозиторий |
| Событие | ╔══╗ | Публикация, релиз, конференция |

## Как отвечать на каверзные вопросы защиты

### Q1: Почему именно 4 типа сущностей, а не 5 или 6?

**Ответ:** 4 типа (субъект, ресурс, событие, индикатор) — минимальный достаточный набор для карты связей. Добавление дополнительных типов (документ, публикация, роль) не увеличивает аналитическую ценность, а снижает читаемость. Каждая сущность однозначно относится к одному типу, что упрощает интерпретацию.

### Q2: Чем «подтверждено» отличается от «вероятно»?

**Ответ:** «Подтверждено» — прямое указание в источнике (WHOIS, DNS, HTTP 200/302, OAuth-спецификация). «Вероятно» — косвенное подтверждение (совпадающие DNS-паттерны, одинаковые команды, совпадающие домены). Разница в том, что подтверждённые связи можно проверить и воспроизвести, вероятные — требуют дополнительной верификации.

### Q3: Как вы знаете, что 20 связей — достаточно?

**Ответ:** Минимальное требование — 20 связей. В работе может быть больше, если данные позволяют. Главное — не количество, а качество: каждая связь должна иметь основание (доказательство) и источник. Карта из 20 качественных связей ценнее карты из 50 необоснованных.

### Q4: Почему вы не использовали графовые базы данных для визуализации?

**Answer:** ASCII-визуализация выбрана для простоты и воспроизводимости. Графовые базы (Neo4j, Gephi) требуют дополнительного инструмента. ASCII-карта выполняет ту же функцию: показывает структуру связей и доступна в текстовом формате. Главное — не инструмент визуализации, а табличная модель сущностей и связей.

### Q5: Как вы отделяли текущие связи от исторических?

**Answer:** Историчность определялась по трём маркерам: HTTP-статус 404 (исключён), Archive.org (исторический), официальные источники выделения (EVT-02). Текущие сущности подтверждены HTTP 200/302, DNS-записями, актуальной документацией.

### Q6: Что если карта не приводит к аналитическому выводу?

**Answer:** Если карта не приводит к аналитическому выводу, она остаётся иллюстрацией, а не результатом OSINT-анализа. В нашей работе карта показывает, что публичный цифровой контур — это не единый ресурс, а сеть из нескольких устойчивых групп, что невозможно увидеть при чтении отдельных страниц.

### Q7: Как вы проверяли, что не пропустили важные связи?

**Answer:** Проверка полноты — через перекрёстную проверку источников. Каждый источник (DNS, официальный сайт, press, blog, archive, OSS) должен быть проверен на наличие сущностей и связей. Если после проверки всех источников связей нет — значит, их нет в публичном доступе.

### Q8: Почему вы считаете выбранные типы связей достаточными?

**Answer:** 5 типов связей (владеет, публикует, содержит индикатор, связало с, выделил) охватывают все наблюдаемые отношения в публичном цифровом контуре. Добавление типов (зависит от, зеркалирует) не увеличивает аналитическую ценность. Карта должна быть минимально достаточной.

### Q9: Что делать, если одна сущность подходит под два типа?

**Answer:** Сущность относится к одному типу по определению:
- Если субъект действует, публикует, владеет → субъект
- Если ресурс — цифровой объект с идентификатором → ресурс
- Если событие — факт во времени → событие
- Если индикатор — наблюдаемый признак → индикатор

Например, domain.com — ресурс (цифровой объект). Его DNS-запись — индикатор. OAuth-домен — ресурс, хотя и связан с событием авторизации.

### Q10: Как карта связей помогает в интересах информационной безопасности?

**Answer:** Карта связей позволяет:
- Выявить несанкционированные ресурсы (неофициальные домены, поддомены)
- Отслеживать эволюцию цифрового контура (исторические изменения)
- Выявить косвенные связи между субъектами (партнёрства, acquisitions)
- Оценить устойчивость инфраструктуры (количество подтверждённых связей)
- Выявить потенциальные точки атаки (слабо подтверждённые связи, исторические артефакты)
