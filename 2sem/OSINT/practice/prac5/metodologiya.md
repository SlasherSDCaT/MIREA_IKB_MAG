## 1. Общий подход к выполнению работы

### Что требуется сделать

Практика 5 — это **мост между ручным OSINT-анализом (практики 2–4) и аналитической обработкой данных**. Вам нужно не просто собрать и описать следы, а **автоматизировать их структурирование**: нормализовать, классифицировать, разметить и проверить качество автоматической обработки.

**Ключевое отличие:** ценность OSINT начинается не с «нашёл ссылку», а с «превратил массив разрозненных артефактов в осмысленную картину». Автоматизация — это инструмент, а не замена анализу.

### Чем практика 5 отличается от предыдущих

| Практика 2 | Практика 3 | Практика 4 | Практика 5 |
|---|---|---|---|
| Ручной сбор + оценка рисков | Реконструкция полного контура | Сравнительный анализ 3 объектов | **Автоматизация обработки следов** |
| 8+ следов, 5+ публикаций | 15+ связанных доменов | 7+ критериев сравнения | **30+ записей + классификатор + автоматизация** |
| Ручная интерпретация | Классификация по уверенности | Отраслевые паттерны | **Алгоритм классификации + верификация** |
| | | | **Журнал ошибок автоматизации** |

### Рекомендованный объект

**Яндекс** (вариант 4 — SaaS-сервис):
- Богатый набор открытых технических следов (30+)
- Хорошо структурированная документация, вакансии, OSS
- Подходит для демонстрации классификатора и автоматизации
- Данные доступны по тем же источникам, что и в практиках 2–4

## 4. Этап 3. Ручной сбор открытых технических следов

### Шаг 1. Определите, что фиксировать

Минимальный объём — **30 записей**. Каждая запись — это артефакт, который можно интерпретировать:

**Что собирать:**
- Домен, поддомен, служебный URL или email
- Упоминание платформы, облачного провайдера, help-системы, инструмента аналитики
- Упоминание API, SSO, портала документации, CDN
- Указание на технологию в вакансии, статье, презентации
- Историческое упоминание старого домена или сервиса

### Шаг 2. Соберите данные по категориям

#### Доменные и DNS-следы

```bash
# Основной домен
whois yandex.ru → владелец, даты, registrar
whois ya.ru → текущая точка входа
whois yandex.com → OAuth-домен
whois yandex.net → инфраструктурный домен

# DNS
dig yandex.ru NS +short → ns1.yandex.ru, ns2.yandex.ru
dig yandex.ru MX +short → mx.yandex.net
dig yandex.ru TXT +short → v=spf1 redirect=_spf.yandex.ru
dig yandex.ru DNSKEY +noall +answer → DNSSEC включён

# Поддомены через crt.sh
crt.sh?q=yandex.net → cloud.yandex.net, oauth.yandex.net
crt.sh?q=*.yandex.ru → imap, smtp, mc, dr.yandex.ru
```

#### OAuth и API-следы

```
oauth.yandex.com → публичный OAuth2-эндпоинт (PKCE S256)
cloud.yandex.net → CloudAPI (REST/gRPC)
docs.yandex.ru → документация API
developer.yandex.ru → developer portal
```

#### CDN и инфраструктурные следы

```
yastatic.net → DNS A → 37.9.64.225 (AS13238)
dzdcdn.net → CDN Дзена
connect.cdn.yandex.net → edge-серверы
```

#### Публикационные и кадровые следы

```
tech.yandex.ru → 12+ категорий публикаций
github.com/yandex → 65K+ звёзд, OSS-проекты

infraevents.yandex.ru → конференции
```

#### Исторические следы

```

dzen.yandex.net → промежуточный домен Дзена
career.yandex.ru → HTTP 404 (архивный URL)
```

## 5. Этап 4. Нормализация данных и удаление шума

### Шаг 1. Унификация регистра

Все доменные имена приводятся к нижнему регистру:

```
Yandex.ru  →  yandex.ru
MAIL.YANDEX.RU  →  mail.yandex.ru
Cloud.Yandex.Net  →  cloud.yandex.net
```

### Шаг 2. Сокращение длинных URL

Длинные URL с параметрами сокращаются до информативного представления:

```
https://cloud.yandex.ru/operations/yandex-cloud/docs/compute/ → cloud.yandex.ru/operations/
https://tech.yandex.ru/dataengine/data-pipeline/ → tech.yandex.ru/dataengine/
```

### Шаг 3. Разделение «сырой фрагмент» / «нормализованная сущность»

| Сырой фрагмент | Нормализованная сущность |
|---|---|
| `"v=spf1 redirect=_spf.yandex.net"` | `v=spf1 redirect=_spf.yandex.ru` |
| `mx.yandex.net (pri 10)` | `mx.yandex.net` |
| `https://github.com/yandex/ydb/blob/main/README.md` | `github.com/yandex/ydb` |

### Шаг 4. Удаление явных дублей

| Дубль | Исходные формы | Действие |
|---|---|---|
| Почта | `mail.yandex.ru`, `mail.yandex.ru/`, `MAIL.YANDEX.RU` | Унификация к `mail.yandex.ru` |
| Облако | `Cloud.Yandex.Net`, `cloud.yandex.net`, `Cloud yandex.net` | Унификация к `cloud.yandex.net` |
| OAuth | `oauth.Yandex.com`, `oauth.yandex.com` | Унификация к `oauth.yandex.com` |

### Шаг 5. Отметка сомнительных записей

Записи с недостаточным подтверждением отмечаются отдельно:

| Запись | Проблема | Действие |
|---|---|---|
| `oauth.yandex.ru` | DNS-паттерн без HTTP-подтверждения | Пометка «требует проверки» |
| `career.yandex.ru` | HTTP 404 | Пометка «исторический» |

### Что должно получиться к концу этапа

Нормализованный реестр с колонками: сырой фрагмент, нормализованная сущность, удаление дублей, отметки сомнительных записей.

Каждое правило связывает условие с результатом:

### Шаг 4. Задайте порядок применения правил

Порядок важен! Например:
1. Сначала P6 (исторические маркеры имеют наивысший приоритет)
2. Затем P3/P4/P5 (архитектурные/организационные/процессные)
3. Затем P1/P2 (базовые доменные/контактные)
4. Если ни одно не сработало → «Не определена»

### Что должно получиться к концу этапа

Готовый классификатор: 5–8 категорий + дополнительные поля + правила (P1–P6) + порядок применения.

## 7. Этап 6. Реализация частичной автоматизации

### Шаг 1. Выберите инструмент

Допустимые инструменты:
- **Электронные таблицы** (Excel, Google Sheets) — формулы, IF, SEARCH, SEARCH
- **Локальный Python-скрипт** — регулярные выражения, словари
- **Псевдокод** — если скрипт не нужен, опишите логику алгоритма

### Шаг 2. Определите, что автоматизировать

Не автоматизируйте всё подряд. Автоматизация — это повторяющиеся операции:

| Операция | Автоматизируется? | Инструмент |
|---|---|---|
| Классификация по ключевым словам | ✓ Да | IF-формулы / regex |
| Выделение историчности | ✓ Да | Поиск маркеров (archive, 404, redirect) |
| Определение уровня значимости | ✓ Да | По типу источника и подтверждённости |
| Семантическая интерпретация | ✗ Нет | Требует экспертизы |
| Проверка корректности | ✗ Нет | Требует ручной верификации |

### Шаг 3. Реализуйте автоматизацию (пример на Python)

```python
# Псевдокод — реализация классификатора

def classify_trace(raw_fragment, source_type, notes):
    combined = (raw_fragment + ' ' + source_type + ' ' + notes).lower()
    
    # P6 — исторический (приоритет)
    if any(m in combined for m in ['archive', '404', 'redirect']):
        return 'Исторический след', 'архивный'
    
    # P1 — доменный
    if any(m in combined for m in ['.ru', '.com', '.net', '.tech', '.ai']):
        return 'Доменный след', 'текущий'
    
    # P2 — контактный
    if any(m in combined for m in ['mail', 'smtp', 'mx', 'spf', 'dkim']):
        return 'Контактный след', 'текущий'
    
    # P3 — архитектурный
    if any(m in combined for m in ['api', 'docs', 'oauth', 'cloud', 'cdn']):
        return 'Архитектурный след', 'текущий'
    
    # P4 — организационно-технологический
    if any(m in combined for m in ['career', 'tech', 'habr', 'blog']):
        return 'Организационно-технологический след', 'текущий'
    
    # P5 — процессный
    if any(m in combined for m in ['monitoring', 'infra', 'event', 'metric']):
        return 'Процессный след', 'текущий'
    
    # Ни одно правило
    return 'Не определена', 'неясно'
```

### Шаг 4. Определите автоматические поля

Минимум 5 полей:
1. **category** — основная категория (P1–P6)
2. **subcategory_role** — функциональная роль (OAuth, CDN, API, Cloud и т.д.)
3. **significance_level** — уровень значимости (высокий/средний/низкий)
4. **historicity_flag** — признак историчности (текущий/архивный/неясно)
5. **confirmation_status** — статус подтверждения (подтверждено/требует проверки)

### Шаг 5. Заполните таблицу автоматизированной классификации

### Форма 3. Таблица автоматизированной классификации

| ID | Категория | Подкатегория | Уровень значимости | Историчность | Проверено вручную | Комментарий |

### Вопрос 1: Почему вы считаете выбранные категории достаточными для вашего объекта исследования?

**Ответ:** Шесть категорий (доменный, контактный, архитектурный, организационно-технологический, процессный, исторический след) охватывают все аспекты цифрового контура. Для Яндекса все категории релевантны: доменная фрагментация, OAuth-контур, почтовая инфраструктура, технологический блог, Метрика, исторические домены Дзена.

### Вопрос 2: Какие типы следов оказались наиболее информативными?

**Ответ:** Наиболее информативны **архитектурные следы** (OAuth, Cloud, CDN) и **доменные следы** (фрагментация контура). Вакансии и OSS-репозитории (организационно-технологические) дали наибольшее число структурируемых следов, раскрыв технологический стек.

### Вопрос 3: Какие операции вы автоматизировали и почему именно их?

**Ответ:** Автоматизированы: (1) классификация по ключевым словам — повторяемая операция для каждой из 38 записей; (2) выделение историчности — маркеры легко обнаруживаются; (3) определение уровня значимости — зависит от типа источника, который алгоритмизуется. Не автоматизирована семантическая интерпретация (требует экспертизы).

### Вопрос 4: Как вы проверяли качество автоматической классификации?

**Ответ:** Выбрана выборка из 12 записей (31,6%). Каждая проверена вручную: категория, подкатегория, историчность, подтверждение. Сравнены с автоматическими. Выявлено 4 типа ошибок. Скорректированы приоритеты правил.

### Вопрос 5: Какие ошибки алгоритма были наиболее частыми?

**Ответ:** Наиболее частая — **приоритет доменных маркеров над архитектурными** (P1 vs P3). Домены `.com`, `.tech`, `.ai` автоматически классифицируются как «Доменный след», хотя функционально это OAuth и OSS. Вторая ошибка — **потеря OSS-контекста** для `.tech`-доменов.

**Ответ:** Исторические маркируются по маркерам: `archive`, `404`, `redirect`. Внешние данные (web.archive.org, HTTP 404) подтверждают историчность. Текущие помечаются при отсутствии маркеров и подтверждении HTTP/DNS.

### Вопрос 7: Какие ограничения есть у вашего подхода?

**Ответ:** (1) Ключевые слова не учитывают семантику; (2) 33,3% ошибок требуют ручной коррекции; (3) пассивные данные неполны; (4) career.yandex.ru недоступен; (5) web.archive.org не полон.

### Вопрос 8: Какой практический вывод можно сделать по вашему объекту на основе открытых данных?

**Ответ:** У Яндекса наблюдается фрагментированный цифровой контур с доминирующим архитектурным следом, распределённой доменной структурой, полноценной почтовой инфраструктурой и историческими артефактами. ## Как отвечать на каверзные вопросы защиты

### Q1: Почему именно 6 категорий, а не 5 или 8?

**Ответ:** 5 — минимально допустимое количество. 8 — максимальное. 6 — оптимально для Яндекса: доменный, контактный, архитектурный, организационно-технологический, процессный, исторический. Меньше — категории станут слишком широкими (потеря детализации). Больше — категории будут дробными и перекрывающимися (например, «архитектурный» и «доменный» слишком близки при 8 категориях).

### Q2: Почему автоматизация на основе ключевых слов, а не ML-классификация?

**Answer:** Для учебного задания важнее **прозрачность и воспроизводимость**. ML-модель — чёрный ящик: студент не сможет объяснить, почему запись получила ту или иную категорию. Ключевые слова — прозрачны и детерминированы: P1 сработал потому, что `.ru` найден в строке. Это соответствует требованиям магистерской подготовки — студент должен уметь объяснить логику результата.

### Q3: Как вы знаете, что 33,3% ошибок — это нормально?

**Answer:** Мы не считаем это «нормальным» — это результат первого прохода классификатора. Ключевой момент: мы **выявили эти ошибки, скорректировали правила и улучшили качество**. Без ручной верификации мы бы не узнали о проблемах приоритизации P1 vs P3.

### Q4: Почему вы выбрали Яндекс для автоматизации, а не более простой объект?

**Answer:** Яндекс — идеальный тестовый объект: богатый набор следов (30+), разнообразие категорий (все 6 сработали), наличие исторических следов (dzen.yandex.net, career.yandex.ru 404) — именно это позволяет продемонстрировать как срабатывание правил, так и типичные ошибки.

### Q5: Что делать, если запись подходит под несколько категорий?

**Answer:** Приоритет определяется порядком правил: сначала P6 (исторический), затем P3 (архитектурный), затем P1/P2 (базовые). Если запись `oauth.yandex.com` подходит и под P1 (`.com`), и под P3 (`oauth`), то P3 имеет приоритет. Это зафиксировано в классификаторе.
