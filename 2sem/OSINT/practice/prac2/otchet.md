## 5. Схема публично раскрываемого цифрового контура Яндекса

Поскольку работа выполняется в текстовом формате, схема представлена в виде структурной схемы, реконструированной по пассивным данным.


![Схема](/sessions/happy-magical-gauss/mnt/outputs/diagrams/prac2_public_contour.png)


**Пояснение к схеме:**

Схема показывает **три уровня** публично наблюдаемого контура:

1. **Источники сбора данных** — пассивные источники, через которые внешний наблюдатель может получить информацию (вакансии, блоги, документация, open-source, DNS/TLS/ASN-реестры, архивы).

2. **Публичные доменные сервисы** — все сервисы, домены и поддомены, наблюдаемые через DNS, TLS-сертификаты и HTTP-запросы. Показаны основные продукты: поиск (ya.ru), статический контент (yastatic.net), авторизация (OAuth), облачные сервисы (Cloud API), CDN (70+ edge-серверов), почта (imap/smtp), медиа (dzen.ru).

3. **Внутренняя инфраструктура (реконструированная)** — сервисы, которые удалось реконструировать по открытым данным:
   - YDB (распределённая SQL-база) и YTsaurus (платформа big data) — ядро инфраструктуры
   - NWS (собственная веб-серверная платформа)
   - Монорепозиторий Аркадия, CI/CD-цепочка, система оркестрации

1. **Вакансии:** детализация стека (Salt, ArgoCD, конкретные версии фреймворков) может помочь реконструировать инфраструктуру. Достаточно общих формулировок: «системы оркестрации», «распределённые БД».

5. **CSP-заголовки:** хотя это не публикация, а HTTP-ответ, они раскрывают полный инвентарь доверенных доменов. Организации стоит минимизировать CSP до необходимого минимума.

## 8. Корреляция публикаций и следов

Различные источники складываются в целостную картину следующим образом:

### Вакансии + технические статьи
Вакансии показывают **«что»** (конкретные инструменты и технологии), а технические статьи — **«почему»** и **«как»** (архитектурные решения и причины выбора). Совместно они дают полную картину технологического стека.
- Вакансия SRE: «Ansible/Salt, Terraform, Docker, k8s, Helm, CI/CD»
- Статья Habr (Apphost): «Apphost — сервис-фасад, граф зависимостей, три слоя»
- **Вывод:** Яндекс использует Kubernetes + Terraform для IaC + собственный сервис маршрутизации Apphost.

### Конференционные доклады + open-source
Конференционные доклады раскрывают **масштабы** (9 ПБ, 700 млн метрик/сек), а open-source проекты — **архитектуру** (YDB: ACID, multi-tenant, serverless; YTsaurus: MapReduce, NoSQL, distributed file system).
- **Вывод:** YDB и YTsaurus — фундаментальные компоненты инфраструктуры, подтверждённые и масштабом, и open-source кодом.

### DNS/сертификаты + OAuth/Cloud API документация
DNS подтверждает **существование** доменов, сертификаты — **периоды активации**, а документация OAuth/CloudAPI — **интеграционные контуры** для внешних клиентов.
- **Вывод:** Все сервисы связаны единой инфраструктурой (own DNS, ASN, CDN) с публичными API-контуром для внешних интеграций.

### CSP-заголовок + yastatic.net
CSP-заголовок `content-security-policy` — **пассивный артефакт**, который содержит полный инвентарь доверенных доменов. `yastatic.net` — связующий домен для статического контента.
- **Вывод:** CSP-заголовок сам по себе является мощным источником технических следов, раскрывающим список всех внутренних сервисов.

### Архивы + текущие данные
Эволюция почтового MX-шаблона, регистрация yastatic.net (2013 → текущее состояние), миграция yandex.ru → dzen.ru (2022) — показывают **историческую трансформацию** инфраструктуры.

1. **Пассивные методы.** Все источники использованы без активного сканирования, проб доступа или тестирования уязвимостей.

6. **Работа не включает проверку доступности, производительности или уязвимостей** реальных систем.
7. **Некоторые внутренние сервисы и технологии не упоминаются публично** и потому не могут быть обнаружены пассивным анализом.

## 10. Ответы на вопросы для защиты

### 1. Почему выбранные вами публикации относятся к рискованным?

Публикации отнесены к рискованным на основе критерия **информативности**: публикация раскрывает больше сведений о цифровой инфраструктуре, чем необходимо для её основной функции. Например, вакансия SRE не нуждается в перечислении конкретных CI/CD-инструментов (ArgoCD, TeamCity, Spinnaker) — достаточно общих формулировок. Конференционный доклад не обязан содержать точные цифры (9 ПБ, 700 млн метрик/сек) — общие описания достаточны. Это повышает информированность внешнего наблюдателя о внутренних процессах и инфраструктуре.

### 2. Какие технические следы вы считаете наиболее надёжно подтверждёнными?

- **NS-серверы** `ns1.yandex.ru`, `ns2.yandex.ru` — прямой факт владения DNS-инфраструктурой.
- **SPF-редирект** `_spf.yandex.net` — прямое доказательство централизованного почтового контура.
- **ASN AS200350** через bgp.he.net — официальный реестр ASN.
- **SSL-сертификаты** через Certificate Transparency logs — неизменяемый публичный реестр.
- **DNSSEC** (RRSIG + DNSKEY) — криптографическое подтверждение.
- **HTTP-заголовок `Server: nws`** — прямое указание на собственную веб-платформу.

### 3. Какие выводы нельзя делать по вашим данным и почему?

- **«Яндекс использует multi-cloud»** — достаточно одного факта Yandex Cloud, но нет прямых данных о других провайдерах.
- **«Все внутренние сервисы реконструированы»** — публичные данные дают лишь частичную картину.
- **«Все вакансии отражают текущее состояние»** — могут быть гипотетическими или устаревшими.
- **«Точная топология известна»** — публичные данные не содержат IP-диапазонов и полных схем.

### 4. Как разные публикации дополняют друг друга?

Каждый источник даёт свой фрагмент пазла:
- **Вакансии** → технологический стек и инструменты
- **Блоги и статьи** → архитектурные решения и контекст
- **Доклады** → масштабы и производительность
- **DNS/сертификаты** → подтверждение существования доменов
- **Документация** → интеграционные контуры и API-паттерны
- **Open-source** → архитектура внутренних систем
- **Архивы** → эволюция инфраструктуры во времени
- **CSP-заголовки** → инвентаризация доверенных доменов

Один артефакт редко опасен сам по себе, но в совокупности они образуют целостную картину.

### 5. Какие публикации объекту стоило бы излагать аккуратнее?

- **Вакансии:** заменить конкретные названия инструментов на обобщённые («системы оркестрации» вместо «Kubernetes + ArgoCD + Helm»)

- **Open-source:** проверять конфигурационные файлы на наличие внутренних hostnames
- **CSP-заголовки:** минимизировать до необходимый минимум
