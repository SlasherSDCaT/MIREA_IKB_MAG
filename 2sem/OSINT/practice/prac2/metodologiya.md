## 4. Этап 3. Выявление DNS- и инфраструктурных следов

### Шаг 1. DNS-запросы

Используйте `dig` или digga.dev для проверки записей:

```bash
# NS-серверы
dig yandex.ru NS +short
# Результат: ns1.yandex.ru, ns2.yandex.ru
# Вывод: собственная DNS-инфраструктура

# MX-записи
dig yandex.ru MX +short
# Результат: mx.yandex.net
# Вывод: единый почтовый сервер

# SPF
dig yandex.ru TXT +short
# Результат: "v=spf1 redirect=_spf.yandex.net"
# Вывод: централизованный SPF для всех поддоменов

# DKIM
dig mail._domainkey.yandex.ru TXT +short
# Результат: "v=DKIM1; k=rsa; p=MIGf..."
# Вывод: DKIM-подпись почты

# DNSSEC
dig yandex.ru DNSKEY +noall +answer
# Результат: RRSIG + DNSKEY записи
# Вывод: включённый DNSSEC
```

**Аналогично для ya.ru, cloud.yandex.net, dzen.ru** — проверяете NS, MX, CNAME.

### Шаг 2. ASN-данные

Заходите на bgp.he.net, вводите IP-адрес yandex.ru:

```
ASN: AS200350 (YANDEX LLC)
Хостинг: Yandex Cloud
Количество доменов: 57 000+
```

Вывод: крупная автономная система для облачного сервиса.

### Шаг 3. CDN

Заходите на `connect.cdn.yandex.net` и смотрите информацию о наличии edge-серверов:
- 70+ серверов
- Прямые подключения на 10+ IX РФ (Sea-IX, SIBIR-IX, MSK-IX, Piter-IX, DVO-IX)

### Что должно получиться к концу этапа

Не менее 8 технических следов, классифицированных по категориям (доменные, почтовые, инфраструктурные, сетевые).

- Периоды валидации (когда сервис был активен)

### Шаг 2. CSP-заголовки

Откройте `ya.ru` или любую страницу Яндекса, нажмите F12 → Network → нажмите на любой запрос → посмотрите Headers:

```
Content-Security-Policy:
  connect-src 'self' blob: yandexmetrica.com:* ads.adfox.ru mc.admetrica.ru
  script-src 'self' blob: 'nonce-8262' ads.adfox.ru mc.yandex.ru yastatic.net
  img-src * 'self' data: blob: *.yandex.net *.s3.yandex.net
  ...
```

**Вывод:** CSP-заголовок раскрывает полный инвентарь доверенных доменов — это мощный пассивный след.

### Шаг 3. Заголовок Server

В тех же Headers найдите:
```
Server: nws
```

**Вывод:** собственная веб-серверная платформа, не Apache/Nginx.

## 8. Этап 7. Построение схемы и аналитические выводы

### Шаг 1. Постройте схему

Реконструируйте цифровую инфраструктуру по пассивным данным:

```
Источники → Публичные сервисы → Внутренняя инфраструктура → Третьи стороны
```

**Важно:** показывайте то, что удалось **реконструировать по открытым данным**, а не «внутреннюю сеть» — вы её не видите.

### Шаг 2. Сформулируйте выводы

Разделите на три категории:

**Подтверждённые** (есть прямые доказательства):
- NS-серверы own (dig)
- SPF-редирект (dig)
- ASN AS200350 (bgp.he.net)
- Server: nws (curl)

**Вероятные** (косвенные признаки, но логичные):
- Микросервисная архитектура (вакансии + статьи)
- Event-driven с Kafka (вакансии + доклады)
- Мониторинг: Prometheus + Grafana (вакансии SRE)

**Требуют проверки** (недостаточно данных):
- Точное количество сервисов (расходящиеся данные)
- Multi-cloud наличие
- Полная топология

### Шаг 3. Ограничения

Обязательно укажите:
- Пассивные методы
- Вакансии могут содержать гипотетические технологии
- Архивы неполные
- Не проверена доступность и уязвимости

## Как отвечать на вопросы защиты

### Вопрос 1: Почему выбранные публикации рискованны?

**Ответ:** «Риск определяется не наличием уязвимости, а информационной полезностью для внешнего наблюдателя. Если публикация раскрывает больше о цифровой инфраструктуре, чем нужно для её функции — она рискованна. Например, вакансия DevOps не нуждается в перечислении конкретных CI/CD-инструментов (ArgoCD, TeamCity), а статья про архитектуру не обязана содержать конкретное количество микросервисов (180+).»

### Вопрос 2: Какие следы наиболее надёжны?

**Ответ:** «Надёжность определяется независимым подтверждением. Самые надёжные следы: NS-серверы (проверяются через dig), SPF-запись (проверяется через DNS), ASN AS200350 (официальный реестр bgp.he.net), SSL-сертификаты (Certificate Transparency logs — неизменяемый реестр), DNSSEC (криптографическая подпись).»

### Вопрос 3: Какие выводы нельзя делать?

**Ответ:** «Нельзя утверждать точную топологию внутренней сети, наличие multi-cloud, что все вакансии отражают текущее состояние. Пассивные данные дают лишь частичную картину — для этого нужен активный анализ. Также нельзя делать выводы об отсутствии сервисов — их просто не видно.»

### Вопрос 4: Как публикации дополняют друг друга?

**Ответ:** «Каждая публикация даёт свой фрагмент: вакансии показывают инструменты, статьи — архитектуру, доклады — масштаб, DNS/TLS — подтверждение существования, документация — интеграционные контуры, open-source — архитектуру внутренних систем, архивы — эволюцию. Один артефакт редко опасен, но в совокупности они образуют целостную картину.»

### Вопрос 5: Что стоило бы публиковать аккуратнее?

**Ответ:** «Вакансии — конкретные названия инструментов, конференционные доклады — точные цифры масштаба, технические статьи — названия внутренних сервисов, open-source — конфигурационные файлы с hostnames, CSP-заголовки — минимизировать до необходимого минимума.»

### Вопрос 6: Почему работа — пассивный анализ?

**Ответ:** «Все источники использованы без какого-либо активного воздействия: DNS-запросы через публичные рекурсивные DNS, SSL-сертификаты из публичных logs, вакансии и блоги — публичные веб-страницы, ASN — публичные реестры. Ни один метод не включает сканирование, проб доступа, брутфорс или тестирование уязвимостей.»

### Вопрос 7: Какие ограничения у вашего исследования?
